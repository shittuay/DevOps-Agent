# Risk lives on the tool, not in a name-set in safety.py

**Decision:** Phase 1 of the governance refactor (`feat/tool-capability-metadata`).
Every tool may declare a `capability` block (`permission` ladder
`read < analyze < modify < deploy < destroy`, plus `mutating` / `reversible` /
`produces`). `SafetyValidator.validate_tool_call` resolves risk from that —
module-declared > `config/tool_capabilities.yaml` > `None` — **before** its legacy
name-sets, which stay only as a floor. A declaration can raise the risk or hold
it, never lower it. `tests/test_tool_capabilities.py` fails the build if a
medium/high tool has no declared capability, or if a declaration is more lenient
than the legacy rules.

**Why:** `CLAUDE.md`'s Safety System section is a running list of scheduled-audit
findings where a `<provider>_<verb>_<noun>` tool (`register_targets`,
`publish_sns_message`, `create_route53_record`, `create_ec2_keypair`,
`generate_s3_presigned_url`, …) defeated prefix auto-detection and shipped with no
confirmation gate until an audit caught it. The classification lived in a file
the tool doesn't, and nothing failed when someone forgot to edit it. Moving the
metadata onto the tool + a CI gate turns "forgot to classify" from a silent
production gap into a red build.

**Consequences:**
- `config/tool_capabilities.yaml` is generated by
  `scripts/gen_tool_capabilities.py` from the current legacy classification (331
  tools; legacy `high` → `destroy`, `medium` → `modify`). Re-run it after
  changing the legacy sets — a staleness test enforces this.
- The legacy sets and `<provider>_<verb>_<noun>` blind spot still exist; they are
  the floor now, not the primary path. Removed in a later phase once every module
  declares inline.
- `mutating` / `reversible` / `produces` are recorded but unused until the Phase 5
  rollback stack.
- No runtime behaviour change for any existing tool — the generated YAML mirrors
  today's classification exactly, and 964 tests pass unchanged.

Full plan: `docs/governance-refactor.md`. Origin: the `devops-agent-harness`
architecture comparison (2026-09-06), whose `agent/policies/` is a clean-room
version of this idea.
