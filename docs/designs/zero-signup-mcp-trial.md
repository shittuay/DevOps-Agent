## Problem Statement

npm package, an MCP registry listing, and 497 passing tests. It has zero paying
customers and one active user. `TODOS.md` P0 #2 says the gap is distribution and

Production data contradicts that diagnosis. The gap is not reach — it is that
nobody who arrives can start.

## Status Quo

The target user asks ChatGPT or Claude for the command, then pastes it into a
terminal and runs it by hand.

This is the competitor. Not Datadog, not StackGen. It is free, already installed,
already trusted, and good enough. The only thing it lacks is execution and a
safety gate.

## Target User & Narrowest Wedge

**User:** a hands-on DevOps/SRE practitioner who already uses an LLM assistant
daily for cloud operations and runs the output manually.

**Wedge:** give that person execution inside the assistant they already use,
without asking them to sign up, switch UI, or hand over cloud credentials.

The web app fails this test. It asks them to abandon the assistant they trust,
learn a new chat UI, and give an unknown vendor cloud credentials — three costs
for one benefit. The MCP server passes it: it adds execution to the workflow they
already have and asks for nothing in return. Only one of those is strictly
additive to the status quo.

## The Wall

`mcp/bin/server.js` is 85 lines. Line 7:

```js
const API_KEY = process.env.DEVOPSAGENT_API_KEY || '';
if (!API_KEY) {
  '[devops-agent] ERROR: DEVOPSAGENT_API_KEY is not set.\n' +
  '[devops-agent] Get your key at https://devopsagent.io/api-gateway/keys\n'
```

To pass that line a person must: create an account, verify email, complete
onboarding, attach cloud credentials, find the API gateway page, generate a key,
hand-edit their Claude Desktop JSON config, and restart it. Eight steps before
first value.

Two API keys have ever existed. Both are the founder's.

## Premises

All five accepted by the founder on 2026-09-02:

1. There is no demand evidence and no revenue. Every readiness claim in
   `MARKETING_PLAN.md` is about supply, not demand.
2. The binding constraint is activation, not reach. Eight strangers arrived with
   zero marketing; all eight failed to reach a first action. More reach
   multiplies a zero.
3. npm is the only channel showing pull and it dead-ends at a locked door.
4. The web app competes with the status quo; the MCP server completes it.
5. Firing `MARKETING_PLAN.md` now burns one-shot assets (Show HN, Product Hunt)
   against a 0% activation funnel, permanently.

Corollary the founder accepted: the last 83 commits — IDOR fixes, drift detection
rewrite, Cloudflare keep-alive — were correct engineering aimed at a constraint
that was never binding.

## Approaches Considered

### Approach A: Zero-signup MCP trial (CHOSEN)
`npx @devopsagent/mcp-server` auto-provisions an anonymous trial key on first run
and starts in sandbox mode. No account, no cloud credentials, no config editing.
An account is requested only when the user wants to attach a real cloud account.
Effort S/M (human ~1 week / CC ~2-3 hours). Risk Low-Med.
Reuses `services/learning_sandbox.py`, the `api_keys` model, the tier/credit
system, and `routes/api_gateway.py`. New code is one endpoint plus
`mcp/bin/server.js`.

### Approach B: Local-first MCP, hosted as the upgrade
Ship the tools as a local MCP server (`uvx devopsagent-mcp`) using the user's own
`~/.aws` credentials on their machine. No account, no key, no credential handover
ever. Hosted product becomes the team layer (shared audit log, approvals, org
policy, scheduled monitoring). Effort L/XL (human ~4-6 weeks / CC ~1-2 days).
Reuses all 746 tool handlers and `safety.py` unchanged.

**Not chosen now, but this is the destination.** Rejected as the first move
because it puts four to six weeks between today and the first stranger touching
the product — the same trap as the last six months, with better architecture at
the end of it.

### Approach C: Open-source the safety layer
Rejected during the session: gives away the most defensible asset
(`src/agent/safety.py` risk classification across 746 tools) to buy distribution,
and is hardest to convert into revenue. The founder needs revenue evidence, not
GitHub stars.

## Recommended Approach

**A, built as a probe pointed at B.**

A is the only option where a human who is not the founder completes a first
action inside two weeks. Until that observation exists, every larger bet is
guesswork. Design A so its pieces (sandbox-first default, credential-optional
tool execution) are reusable by B rather than thrown away.

## Open Questions

1. **Abuse bound on anonymous keys.** Free tier is 20 Kimi credits, so the
   marginal cost is small, but the endpoint is unauthenticated by construction.
   IP rate limit? Proof-of-work? Cap on concurrent anonymous keys? Unresolved.
2. **Sandbox-first vs. real-cloud-first.** Sandbox removes the credential barrier
   but the first impression is simulated. `CLAUDE.md`'s standing rule requires
   `[Sandbox]` labelling, which is honest but weakens the demo. Does a simulated
   first run convert, or does it read as a toy?
3. **Who is the named human?** The founder confirmed a specific person exists and
   described their workflow, but the name and title were not captured in session.
   Needed before any outreach copy is written.
4. **Does the anonymous account upgrade cleanly?** An anonymous key must be
   claimable into a real account without losing history, or the conversion step
   becomes its own wall.

## Review Outcome (plan-ceo-review, 2026-09-02, HOLD SCOPE)

28 decisions taken. Full record in the review report below. Four things changed
in this design as a result:

1. **D18 was revised by D27.** Full sandboxing of trial tool calls was replaced by an
   allowlist restricted to credential-gated tools. Reason: mocking every call meant the
   trial delivered simulation while the stated wedge is execution, so the probe could not
   falsify its own hypothesis. Credential-gated tools fail closed with "connect an
   account", which becomes the claim moment.

2. **Implementation is gated on verification (D26).** Before any of the build tasks run:
   discriminate the npm signal (journald 401 counts on `/mcp/`, web hits on
   `/api-gateway/keys`, per-version npm downloads), and measure what a 699-tool /
   334,740-byte `tools/list` does to a real Claude Desktop session. Either result can
   invalidate this plan's premise. The "~152 installs/month" figure in Demand Evidence
   above is **unverified** and the 80%-noise discount applied to it was a guess.

3. **Open Question 1 was misframed.** It assumed 20 Kimi credits bound trial abuse.
   `routes/mcp.py` deducts no credits and never calls `check_rate_limit`, so the MCP
   surface has no quota at all today. Metering is a precondition, not a mitigation.

4. **Sunset condition (D24).** This trial machinery is a disposable probe, not a feature.
   When the probe answers its question, either Approach B replaces it or the trial path
   is deleted: the endpoint, the `is_trial` column and its deny-list, the claim flow, and
   any remaining shadow `User` rows. The sandbox/allowlist work on the MCP path and the
   `UsageLog`/`ConversionEvent` instrumentation are permanent and stay.

**Recorded but not added to TODOS.md** (user narrowed the selection): MCP path has no
metering of any kind; `tools/list` is 334,740 bytes / ~84k tokens with `tool_selection.py`
bypassed; `MARKETING_PLAN.md` and the TODOS feature-freeze line are both false records;
`_ensure_subscription()` extraction (TODOS.md:131 falsely marked DONE); shadow-user TTL;
trial-provisioning spike alert; missing `[Sandbox]` markers in `_mock_aws_list`/`_mock_k8s`/
`_mock_azure`; npm publish CI automation.
