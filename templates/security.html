We never need your access keys

Handing an AI agent your cloud credentials is a big ask. Here is exactly how DevOps Agent earns that trust — and how you can verify every claim yourself.

🔑

IAM role delegation, not stored secrets

The recommended way to connect AWS is a cross-account IAM role — the same model used by Datadog and every credible cloud vendor. No long-lived key ever leaves your account.

  • You create the role in your own account — one click via our CloudFormation quick-create, or manually from our published instructions
  • External ID required — protects against confused-deputy attacks
  • Temporary credentials only — we assume the role via STS for 1-hour sessions; nothing long-lived is stored
  • Instant revocation — delete the role (or the CloudFormation stack) and our access is gone, immediately
  • Prefer access keys for a self-hosted setup? Supported, encrypted at rest — but the role is always the recommended path
🔍

Auditable least-privilege policies

Don't take our word for what the agent can touch — read the exact policy JSON before you connect. Your security team can review every action we request.

  • Read-only policy (recommended start): discovery, cost analysis, and security scanning — metadata only, never your data
  • No s3:GetObject — we see bucket configuration, never object contents
  • No secretsmanager:GetSecretValue, no ssm:GetParameter — secret values stay unreadable
  • No lambda:GetFunction — we read function configuration, never your code
  • Management policy: full agent capability, but IAM stays read-only (no privilege escalation) and secret values stay excluded
  • Automated tests in our CI pipeline fail the release if any change weakens these guarantees
🧪

Start in sandbox — no credentials needed

You don't have to connect anything to evaluate DevOps Agent. Sandbox mode gives you the full agent experience against simulated infrastructure.

  • Every tool runs against realistic mock resources — zero access to any real account
  • Practice incident response, cost optimization, and Kubernetes troubleshooting risk-free
  • Enable it in Settings → Preferences, or just skip the credential step during onboarding
  • Connect a real account later, only when you're ready
🔒

Encryption & isolation

Anything you do store with us is encrypted and isolated per user.

  • Credentials encrypted at rest with Fernet (AES-128-CBC + HMAC) before they touch the database
  • All traffic encrypted in transit (TLS via Cloudflare)
  • Strict per-user isolation: conversations, credentials, resources, and findings are scoped to your account in every query
  • Platform secrets live in AWS Secrets Manager, not in code or config files
🛡

Guardrails on every action

An agent that can touch infrastructure needs more than good intentions. Every message and every tool call passes through layered checks.

  • Three-layer prompt defense: input sanitization, an independent AI harmlessness pre-screen, and a hardened system prompt that rejects injection and impersonation
  • Risk classification for all 745 tools: destructive operations (delete, terminate, destroy) always require your explicit confirmation
  • Production escalation: high-risk actions targeting production resources are escalated to critical
  • Repeated abuse attempts lock the account automatically
👤

Account security

Standard protections on the account itself, on by default.

  • Passwords hashed with bcrypt; email verification required for new accounts
  • Multi-factor authentication: authenticator app (TOTP), email, or SMS
  • Automatic lockout after 5 failed login attempts
  • Role-based access control for teams (admin / approver / user / viewer) with audit logging
📧

Found a vulnerability?

We want to hear about it. Email security@devopsagent.io and we'll respond within 48 hours. Please include reproduction steps and give us reasonable time to fix before public disclosure.
